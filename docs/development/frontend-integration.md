# 프런트엔드 연결 명세

[문서 안내](../README.md)

현재 실행 코드에 맞춘 웹 담당자용 연결 계약입니다. AI 기능을 추가하면서 웹에 영향을 주는 요청·응답·처리 규칙도 이 문서에서 함께 갱신합니다. 미구현 기능은 아래에서 구분합니다.

## 담당과 코드 기준

### 2026-11-10 · Part 4 프런트 데모 추가

- 영입 후 월별 활동 안내 다음에 2년 차 목표를 선택한다. 선택값은 게임 ID별 브라우저 메타데이터이며 HTTP 필드는 추가하지 않는다.
- 서버 12개월 직후나 기존 Part 3 완료에서 명시적으로 13~24개월 데모를 열 수 있다. 독립 저장과 기존 통합 저장의 `stage: 'part4'`를 지원한다. 기존 저장은 보존하며 목표가 없으면 진입 전 선택한다.
- `Part4Save`는 [part4State.ts](../../frontend/src/part4State.ts)의 프런트 전용 계약이다. `Game`·`TurnInput`·서버 DB·실제 AI는 변경하지 않는다. 서버 오류의 대체 경로로 사용하지 않는다.
- 국내/해외 분기·필수 면담·사진 매핑·결말·수익은 [Part 4 데모 규칙과 서버 차이](part4-frontend-demo.md)를 참고한다. 웹 담당은 추가 API 작업 없이 적용할 수 있다. 서버의 동일 흐름 구현·서버 저장과의 통합은 미구현이다.

- AI 모듈은 입력 해석·인물별 문맥 구성·대사 생성·출력 검증을 담당합니다.
- 게임 백엔드는 대화방, 행동 실행, 성공·실패·수치·이벤트·엔딩 확정과 저장을 담당합니다.
- 프런트는 입력을 보내고 서버가 확정한 상태와 기록을 표시합니다. 대사로부터 실행 완료나 상대 전환을 추측하지 않습니다.

| 기준 | 위치 |
|---|---|
| 프런트 자료형 | [types.ts](../../frontend/src/types.ts) |
| HTTP 요청 및 쿠키 전달 예시 | [api.ts](../../frontend/src/api.ts) |
| 경로·요청 모델 | [main.py](../../backend/app/main.py), [models.py](../../backend/app/models.py) |
| 응답 구성·처리 순서 | [service.py](../../backend/app/service.py) |

실행 서버의 `/docs`에서 요청 스키마를 확인할 수 있습니다. 현재 응답에는 별도 `response_model`이 없어 응답 전체 스키마가 자동 문서화되지는 않습니다. 응답 필드는 이 문서·자료형·서비스 구현을 함께 확인합니다.

## 2026-11-10 · 화면 확인 후 나레이션·첫 달 면담 수정

- 나레이션은 공통 `NarrationScene`으로 원본 배경·장소/월 제목·넓은 흰 대사창을 표시한다. 기본 프롤로그·1~6개월·Part 3 및 기존 로컬 도입에 적용하며 인물·능력치 사이드바·자금 캡슐을 표시하지 않는다.
- 1개월차 첫 대화를 신입 1:1로 자동 연결한다. 기존 공개 대화의 신입·백하연 응답 중 마지막 백하연만 보이던 경로를 면담 시작 경로에서 제거했다. `game.center_interviews`를 1개월에도 반환하며 신입·리안·도하·세인 모두 최소 1회·최대 8회다. 프런트의 기존 멤버 3회 조건은 제거했다. 계획 확정 시 서버도 전원 최소 1회를 검사하고 9번째 개인 채팅은 409로 거부한다. 첫 달은 훈련·규칙 확정이 별도로 필요하므로 8회 소진만으로 월을 자동 종료하지 않는다.
- 3개월 질책 중단 턴의 응답 순서는 `newcomer → yuna → secretary`다. 서버 저장 순서와 화면 읽기 순서를 일치시킨다. 이전 순서로 저장된 중단 턴도 조회·동일 요청 재시도·프런트 대화/기록 표시에서 같은 순서로 정렬한다. 중단 장면 읽음 키는 `stop-v2`를 써서 기존 읽음 위치 때문에 중간 화자부터 재생하지 않도록 한다.
- 면담 중에는 자금·계약 기간 캡슐을 숨긴다. 운영 결정 화면의 자금 표시는 유지한다.
- 사용자 첨부 `무대_정방향.png`를 `/images/scenes/stage.png`에 보관했다. 4개월 도입에서 백하연 안내 직전까지 무대, 그 안내부터 대표실이다. 5개월 도입·대화·예산 화면도 대표실이다. 백엔드·프런트 자료형의 새 변경은 없으며 `center_interviews`의 월 범위만 확장한다.

## 2026-11-10 · 1~6개월차 실제 서버 흐름 연결

이 항목이 아래의 이전 3~6개월 브라우저 데모·통합 플레이 이력보다 우선한다. 사용자 확정 수치와 판정은 [월별 서버 규칙](monthly-server-rules.md)을 따른다.

- 기본 `/`는 후보·1~6개월을 같은 서버 게임으로 진행한다. `App`의 3개월 진입 시 `SixMonthDemo` 자동 전환을 제거했다. 1개월 화면은 유지하고 2~6개월은 `ServerPartTwo`에서 intro의 인물·단일 흰 대화 영역·공통 `ChatComposer` 배치를 사용한다. `ServerMonthly`, 독립 DEV fixture는 이전 검토용이며 기본 2~6개월 경로가 아니다.
- `game.center_interviews`는 이제 2개월 및 공개 질책 중단 후 3개월에 반환한다. `members`, `turn_limit=8`, `can_finish`, `missing_member_ids` 계약을 공유한다. 실제 상대 답변이 저장된 1:1 채팅만 횟수에 포함한다. 전원 1회 이상이면 직접 종료, 전원 8회면 마지막 답변과 결과를 한 트랜잭션으로 저장한다. 8회가 끝난 멤버에게 추가 채팅은 409, 상대 변경은 가능하다. 공개 중단 요청·대상 전환은 면담 횟수가 아니다.
- 2개월 종료 행동은 `finish_center_interviews`, 3개월은 `mediate_rehearsal`이다. 최소 면담 미충족 시 같은 월에서 백하연 안내만 반환한다. `turn.month_completion.month`는 `2 | 3`; 3개월에는 판정 당시 `fatigue`, `fatigue_max_exclusive=60`도 포함한다. `teamwork`는 결과 보상 적용 전 수치다. 최종 수치·보상은 `game.stats`, `turn.stat_delta`만 표시한다.
- 3개월 중단 턴은 세인·신입이 실제 provider 생성 경로로 답한다. 프런트는 이 답변들을 순서대로 읽은 뒤 면담을 표시한다. demo provider는 명시적인 고정 응답이며 유료 AI 품질 검증이 아니다.
- 4개월은 `encourage_newcomer`, `apologize_on_stage`, `respond_press`, `request_member_support` 중 하나를 실행하면 결과와 다음 월을 함께 저장한다. 이전 `hold_showcase` 경로와 기사 대응 필수 조건은 제거했다. `game.showcase_awareness_start`는 4개월 진입 시 인지도이며 서버 상태에 저장한다. 비용은 4개월 결정 턴에서 한 번만 차감한다.
- 4~6개월 대화 상대는 백하연만 제공하며 필수 면담·8회 제한이 없다. 5개월에는 `game.promotion = {track:'A'|'B', budget_won, minimum_percent:{shortform,radio,fansign}}`가 반환된다. 채팅은 홍보 계획을 상의하는 용도다. 화면에서 예산 배분 창을 안내하고, 금액 확정은 아래 요청으로 처리한다.

```json
{
  "request_id": "promotion-example-001",
  "state_version": 25,
  "input_type": "action",
  "action_id": "allocate_promotion",
  "text": "",
  "promotion_allocation": {
    "shortform_won": 20000000,
    "radio_won": 8000000,
    "fansign_won": 12000000
  }
}
```

- 예시는 A트랙 4천만 원이며 B트랙은 총 1천만 원이다. 각 값은 음수가 아닌 정수 원 단위이며 합계가 해당 총예산과 정확히 같아야 한다. 부적합·잔액 부족은 422, 지출·월 이동 없음. 성공 턴에 `promotion_allocation`, `promotion_track`을 보존한다. 요청 ID·버전·배분 금액을 동일하게 재시도하면 비용·보상은 중복되지 않는다. 프런트는 금액을 로컬 스텟에 반영하지 않는다.
- 6개월은 `chat`으로 `accept_offer` 또는 `recommend_other`를 해석한다. 질문·부정·모호한 지시는 기존 분석·검증을 거치며, 거절 분기는 제거했다. 예능 성장 판단은 현재 서버의 `training_history`에 `variety`가 있는지로 연결한다. 팀원의 실제 능력치·성장 이력 기능 도입 시 이 판정 입력을 함께 맞춰야 한다.
- 2~6개월 결과 턴의 `result_narration`은 서버가 확정한 성패 나레이션이다. 4·6개월 `event_openings[].beats`는 `{character_id,name,text}[]` 형태의 순서 있는 도입이며 `narrator`, `reporter`는 장면 화자 ID로만 사용한다. AI 대화의 `SpeakerRole`에는 추가하지 않는다. 6개월 브리핑은 진입 당시 스텟·주의점을 저장한 순서를 유지한다.
- 6개월 결과를 읽고 결산에서 **7개월차로**를 눌러야 로컬 Part 3를 만든다. `prom-playthrough-v2:{game_id}`를 사용하며 기본 플레이의 `six`는 null, `source`는 서버 6개월 완료 상태다. 이전 v1 데모 저장은 가져오지 않는다. 기존 테스트 진행의 이전·보존은 사용자 요청 범위에서 제외했고 새 게임부터 확인한다.
- 미구현/다른 담당: 대화 의미에 따른 팀워크·피로도 변화, 실제 개별 능력치 +1 및 성장 이력. 이번 변경은 이 효과를 임의로 만들지 않으며 판정은 서버에 저장된 현재 값을 사용한다. 실제 AI 실패는 오류로 반환하고 데모로 대체하지 않는다.
- 적용 순서: 새 백엔드(`models`, `service`, 게임 규칙·콘텐츠·도입)와 `types.ts`·`App`·`ServerPartTwo`·`MonthTwoTransition`·스타일·로컬 키 변경을 함께 적용한다. 이전 프런트의 `hold_showcase`·고정 홍보 행동은 새 서버에서 사용할 수 없다.

## HTTP API

2026-11-10 · 후보 면담 진입 오류 표시: `api.ts`는 네트워크 연결 실패를 `ApiError(status=0)`와 재시도 안내로 표시한다. JSON 오류 본문이 없는 5xx 프록시 응답도 서버 요청 실패로 안내한다. 서버가 반환한 구체적인 오류 메시지와 409·502 상태, 요청 취소는 그대로 유지하며 fixture 성공으로 대체하지 않는다. 진입·저장 API 계약은 변경하지 않았다. 로컬 첫 화면부터 플레이할 때는 프런트와 demo API 서버를 모두 실행해야 한다.

| 메서드·경로 | 입력 | 성공 응답 |
|---|---|---|
| `GET /api/health` | 없음 | `{status, provider}` |
| `GET /api/catalog` | 없음 | `{characters, notice, provider}` |
| `POST /api/games` | `{character_id, scenario?}` | `Game`, HTTP 201 |
| `GET /api/games/{game_id}` | 없음 | `Game` |
| `POST /api/games/{game_id}/turns` | 아래 턴 요청 | `{turn: Turn, game: Game}` |

`character_id`는 catalog의 값을 사용합니다. 생성·조회 응답은 `Game` 자체이며 턴 응답만 `game`으로 감싸져 있습니다. 자유 대화의 이전 기록·스탯·비밀 자료는 프런트가 보내지 않습니다. 서버 저장 상태에서 구성합니다.

현재 소유자 확인은 서버가 설정한 HttpOnly `prom_owner` 쿠키 방식입니다. 게임 ID만으로 다른 브라우저에서 플레이를 복원할 수 없습니다. 기본 프런트는 같은 출처의 `/api`를 사용하고 개발 서버가 백엔드로 중계합니다. 다른 출처로 배포하려면 CORS·쿠키·요청 credentials 설정을 별도로 맞춰야 합니다. API 키는 프런트에 넣지 않습니다.

## 대사별 표정

2026-11-09부터 공통 AI 대사 생성 경로를 사용하는 모든 턴은 월차나 시나리오와 관계없이 `turn.messages[].expression`을 반환합니다. 별도 생성 경로를 사용하는 센터 결정 대화도 같은 필드를 반환합니다. 서버는 대사와 함께 값을 저장하며 `game.history[].messages[]`에서도 같은 값을 읽을 수 있습니다. 표정은 화면 표시용이고 `emotion`은 기존 대사 감정 값입니다.

| `expression` | 이미지 |
|---|---|
| `neutral` | 기본 |
| `excited` | 설렘 |
| `angry` | 화남 |
| `happy` | 기쁨 |
| `sad` | 슬픔 |
| `surprised` | 놀람 |

예를 들어 `{"speaker_id":"haram","text":"제가 센터 후보라고요?","emotion":"anxious","expression":"surprised"}`는 도하의 놀람 표정입니다. 현재 표시 중인 메시지의 `speaker_id`를 그 턴의 참여자 정보로 실제 캐릭터 ID에 연결하고, 그 메시지의 `expression`으로 이미지를 선택합니다. 예전 저장, 사건 도입, 고정 안내 등에서 값이 없거나 해당 이미지 로딩에 실패하면 같은 캐릭터의 기본 표정을 사용합니다. 백하연의 `secretary` 역할은 `baek_hayeon`에 대응합니다.

후보 면담과 Part 2 대화 화면은 현재 대사의 표정을 표시합니다. 표정 파일은 캐릭터별 `frontend/public/images/characters` 폴더에서 관리하며 기본 컷은 `half-body-transparent.png`, 나머지는 `expression-<값>.png`를 사용합니다.

## 턴 요청

각 예시의 요청 ID와 상태 버전은 실제 값으로 교체합니다. `request_id`는 새 의도마다 UUID 등을 생성하고 `state_version`은 마지막 응답의 `game.version`을 사용합니다.

자유 대화와 자연어 상대 전환:

```json
{
  "request_id": "example-chat-001",
  "state_version": 3,
  "input_type": "chat",
  "text": "백 실장이랑 이야기하고 싶어",
  "action_id": null
}
```

선택지 버튼:

```json
{
  "request_id": "example-action-001",
  "state_version": 3,
  "input_type": "action",
  "text": "",
  "action_id": "accept_offer"
}
```

위 행동 ID는 예시입니다. 실제로는 현재 `game.event.actions`에서 선택하고 `used=true`인 버튼은 비활성화합니다.

명시적인 상대 선택:

```json
{
  "request_id": "example-switch-001",
  "state_version": 3,
  "input_type": "conversation",
  "text": "",
  "action_id": null,
  "conversation_mode": "private",
  "target_character_id": "baek_hayeon"
}
```

함께 대화로 복귀할 때는 `conversation_mode="public"`, `target_character_id=null`로 보냅니다. 전환 요청에 발화·행동·`recipient_id`를 섞지 않습니다. 일반 대화에는 전환용 두 필드를 생략합니다. 기존 `recipient_id`는 이번 턴의 청중만 바꾸는 호환 필드이며 새 화면의 지속 전환에는 사용하지 않습니다.

서버 기준 요청 ID 길이는 8~100자, 텍스트는 최대 2,000자, 상태 버전은 0 이상의 정수입니다. 현재 프런트 `TurnInput`은 `text`와 `action_id`를 명시하는 형태입니다. 서버는 생략 시 각각 빈 문자열·null을 기본값으로 사용합니다.

## 상태와 표시 규칙

턴 성공 시 `result.game`으로 현재 상태와 기록을 교체합니다. `turn`을 별도로 기록에 추가하면서 `game.history`도 적용하면 중복될 수 있습니다. 스탯을 프런트에서 다시 누적하지 않습니다.

| 데이터 | 화면 처리 |
|---|---|
| `game.character` | 현재 면담 완료보 또는 선발된 육성 대상. 현재 대화 상대와 별개 |
| `game.conversation` | 지금 대화방·참여자·대상 선택 목록 |
| `game.event` | 현재 사건 제목·장소·브리핑·목표·실행 가능한 선택지 |
| `game.event_openings` | 첫 시작과 진입한 사건의 도입 안내 |
| `game.stats` | 확정된 현재 수치. `funds_won`은 원, `fans`는 명, 나머지는 0~100 |
| `game.evidence`, `game.memories` | 플레이어에게 공개된 증거·공유 기억 |
| `game.history` | 서버 순서대로 표시할 과거 턴 |
| `game.ending` | null이면 진행 중. 값이 있으면 엔딩 표시 및 새 턴 입력 차단 |

`stat_delta`는 해당 턴의 변화 표시용입니다. `outcome`은 `pending/success/partial/failure/neutral/ending`을 처리합니다. 일반 대사의 감정은 `anxious/hopeful/tired/relieved/neutral`이며 방향 정보의 감정과 별개입니다. 기존 `turn.image`는 턴 단위 이미지 URL입니다. 대사별 캐릭터 이미지는 아래 표정 규격으로 연결합니다. `analysis`, `ai_trace`, 참조 ID는 디버깅 정보이며 행동 실행이나 상태 계산의 기준으로 사용하지 않습니다.

### 상대와 화자

- 선택 목록은 `game.conversation.available_targets`에서 만듭니다. 서버 성공 전에는 현재 상대를 확정 표시하지 않습니다. 자연어 전환도 같은 응답을 읽으면 목록과 현재 상대가 갱신됩니다.
- `turn.conversation`은 당시 참여자의 스냅샷입니다. 과거 턴을 표시할 때 사용하며 현재 방을 덮어쓰지 않습니다.
- `messages[].speaker_id`는 후보·신입에 `newcomer`, 비서에 `secretary` 역할을 사용합니다. 첫 달 기존 멤버 1:1 대화는 `dahyun/haram/yuna` 역할을 사용하며 실제 ID와 같습니다. 해당 턴의 `conversation.participants`에서 `role` 또는 `id`로 찾아 이름과 인물 ID를 얻습니다. 예전 기록에 스냅샷이 없으면 육성 대상·비서 이름으로 표시하며 새 멤버에게 이전 개인 대화 문맥을 전달하지 않습니다.
- `kind="conversation_change"`이면 `turn.input`을 시스템 안내로 표시하고 빈 `messages`도 정상 처리합니다. 자연어 전환의 원문은 `source_input`, 당시 방은 `previous_conversation`에 있습니다.
- 과거 기록의 `kind`가 없으면 일반 대사로 취급합니다. 대사의 연결 약속만으로 방을 바꾸지 않습니다.

현재 `game.character`는 육성 대상 신입이며, 대화방을 바꿔도 육성 대상·게임 사건·스탯·기존 기억은 바뀌지 않습니다. 공개 방은 `mode=public`, `target_character_id=null`이며 대표·선택 신입·백하연이 참여합니다. 상대의 가용성은 `backend/app/game/conversation.py`에서 결정합니다.

사야를 육성하면서 백하연과 면담하는 응답의 예시입니다. 방 ID는 예시입니다.

```json
{
  "character": {"id": "c", "name": "사야"},
  "conversation": {
    "id": "a-stable-room-uuid",
    "mode": "private",
    "target_character_id": "baek_hayeon",
    "participants": [
      {"id": "player", "name": "대표", "role": "player", "portrait_url": null},
      {"id": "baek_hayeon", "name": "백하연", "role": "secretary", "portrait_url": "/portraits/hopeful.svg"}
    ],
    "available_targets": [
      {"id": "jiwoo", "name": "사야", "role": "newcomer", "portrait_url": "/portraits/hopeful.svg"},
      {"id": "baek_hayeon", "name": "백하연", "role": "secretary", "portrait_url": "/portraits/hopeful.svg"}
    ]
  }
}
```

`portrait_url`은 현재 예시 SVG입니다. 과거 턴은 당시 방의 캡션과 함께 같은 타임라인에 표시합니다.

사진이 연결된 도입·후보 면담·영입 결과·1개월차 화면은 `introContent.ts`의 `characterPortraits`(제공 상반신 배경 제거본), `characterProfiles`(프로필1), `sceneBackgrounds`(정방향 배경)를 사용합니다. 기존 인물 ID와 화자 판정은 유지하며 서버의 `portrait_url`·HTTP 필드·저장 형식을 바꾸지 않습니다. 1개월차는 기존 `portraitPerson`·비서 화자 판정으로 사진을 고르고, 훈련·규칙 선택 시 현재 대화와 사진을 유지합니다. 2026-11-05 적용: 프런트 코드와 `public/images`를 함께 적용하며 웹 담당의 별도 API 수정이나 서버 적용 순서는 필요하지 않습니다.

최종 영입 확정 창은 `RecruitmentResult.tsx`의 `recruitmentPhotos`를 사용해 선발 신입을 배경 있는 상반신 원본(`half-body.png`), 기존 멤버를 프로필2(`profile-2.png`)로 표시합니다. 다른 화면의 사진·화자 대응은 그대로입니다.

#### 상대 전환 처리

- 명시적 전환은 모델 호출 없이 새 방과 상태 버전을 저장하고 `kind=conversation_change` 알림을 기록합니다. 알림은 사용자·NPC 발언으로 AI 문맥이나 지식에 넣지 않습니다.
- 자연어 전환은 `Analysis.conversation_change`의 모드·정식 인물 ID·현재 입력 원문 근거를 검증한 뒤 같은 서버 전환 경로를 사용합니다. 단순 인물 언급·특징 질문·부정·회상·가정은 전환으로 처리하지 않습니다.
- 대상이 없거나 여러 명이면 기존 방에서 되묻습니다. 다음 입력이 이름뿐인 답변이어도 대상을 선택할 수 있습니다. 현재 만날 수 없는 대상은 422, 오래된 버전·종료된 플레이는 409입니다. 해석·검증 실패 시 저장하지 않습니다.
- 전환 요청과 게임 행동·보상을 함께 실행하지 않습니다. `source_input`은 실제 원문, `previous_conversation`은 그 요청을 들은 이전 방입니다. 원문을 새 상대에게 자동 전달하지 않습니다.
- 같은 참여자의 방으로 돌아오면 같은 방 ID를 사용하고, 이전 대화와 인물별 지식을 유지합니다. 방은 새로고침·서버 재시작 후 복원됩니다.
- 일반 공개 자유 대화는 분석 1회 + 생성 2회, 선택지는 생성 2회, 1:1은 해석 1회 + 생성 1회입니다. 자연어 전환·대상 되묻기는 해석 1회 후 생성 없이 안내하며, 명시적 전환은 호출 0회입니다.

청중별 지식 접근·습득·공개 허가는 [인물별 지식과 공개 조건](character-knowledge.md)을 따릅니다.

### 첫 시작·사건 전환

- `event_openings[].after_turn_id=null`인 안내는 첫 사용자 대화 앞에 표시합니다.
- 값이 있으면 해당 `history` 턴 뒤에 표시합니다. `id`를 렌더링 키로 사용하며 새로고침 때 로컬 목록에 다시 누적하지 않습니다.
- 도입의 `narration`, `scene`, `month`, `title`, `messages`, `goal`, `choices`를 표시합니다. 도입 메시지는 역할 ID 대신 실제 `character_id`와 표시용 `name`을 가집니다.
- `opening.choices`는 진입 당시 설명용 목록입니다. 실제 버튼·사용 여부는 현재 `game.event.actions`를 사용합니다.
- 사건을 끝낸 턴의 `event_id`는 이전 사건, `game.event.id`는 다음 사건일 수 있습니다. 이전 결과와 다음 도입을 각각 표시합니다.
- 안내가 아래에 가려지지 않도록 첫 로딩과 사건 전환 후 렌더링 완료 시 스크롤을 조정합니다. 사용자 입력을 추가로 보내서 도입을 요청할 필요가 없습니다.
- 예전 저장의 누락된 현재 도입도 서버가 복원합니다. 새 플레이 생성은 필요하지 않습니다.

도입 응답 예시입니다.

```json
{
  "event_openings": [{
    "id": "stable-opening-uuid",
    "event_id": "m06_variety",
    "after_turn_id": "the-turn-that-finished-training",
    "month": 6,
    "title": "카메라 앞에 설 준비",
    "scene": "대표실",
    "narration": "시간이 흘러 6개월차, 대표실. ...",
    "messages": [{"character_id": "baek_hayeon", "name": "백하연", "text": "대표님, ..."}],
    "goal": "출연 · 다른 멤버 추천 · 거절 중 하나를 확정하세요.",
    "choices": [{"id": "accept_offer", "label": "신입 출연"}]
  }]
}
```

#### 도입 구성과 저장

- `backend/app/content/event_openings.json`과 현재 사건의 브리핑·목표·선택지로 서버가 구성합니다. 모델 호출 없이 데모·실제 모델 모드 모두 표시합니다.
- 인물 이름과 훈련 여부는 현재 프로필·실제 `training_history`를 사용합니다. 미획득 증거·미확정 결말·새로운 과거사를 도입에 넣지 않습니다.
- `State.event_openings`에 최초 도입을 저장하며, 사건 전환 시 다음 도입을 상태·결과 턴과 같은 SQLite 트랜잭션에 저장합니다. 게임·사건으로 결정되는 안정적인 ID로 중복 생성을 막습니다. 생성·검증 실패나 DB 충돌 시 다음 도입도 저장하지 않습니다.
- 도입은 일반 사용자 턴이 아니므로 행동 근거나 보상으로 처리하지 않습니다. 분석·일반 대사에는 현재 `event_opening`을 전달하고, 결과·엔딩 대사에는 새 도입을 넣지 않습니다. 미래 도입 ID의 인용은 거부합니다.
- 문구 변경 후 백엔드를 재시작하면 새 진입부터 적용합니다. 저장된 도입은 당시 스냅샷을 유지하며, 도입 전용 문구가 없는 사건은 기본 브리핑·목표로 구성합니다.

## 오류·재시도·복원

- 처리 중에는 다른 발화·행동·상대 전환을 막습니다. 실패 후 재시도 대기 중에도 미확정 요청을 보존합니다.
- 네트워크 단절·5xx이면 같은 요청 ID·버전·본문으로 재시도합니다. 서버가 이미 저장했을 수 있으므로 새 ID로 같은 행동을 보내지 않습니다. 성공 응답은 저장된 턴과 최신 게임 상태를 반환합니다.
- 409이면 최신 게임을 조회하고 화면을 갱신합니다. 같은 요청 ID를 다른 본문으로 재사용하거나 오래된 버전을 보내도 409입니다. 자동으로 새 ID를 만들어 행동을 다시 실행하지 않습니다.
- 422이면 요청·허용 대상·행동을 확인하고 서버 안내를 표시합니다. `GameError`는 `{error: string}`이고, 요청 형식 검증의 422는 FastAPI의 `{detail: [...]}`일 수 있습니다. 현재 클라이언트는 후자에 일반 오류 문구를 사용합니다.
- 404이면 현재 브라우저가 소유한 플레이가 없을 수 있습니다. 쿠키가 유효한 상태에서 저장한 게임 ID로 조회해 복원합니다. 일반 연결 플레이 ID는 localStorage의 `prom-story-game`에 보관합니다. 이전 축약 데모의 `prom-game`은 별도이며 자동으로 덮어쓰지 않습니다.
- 실제 모델 오류를 데모 성공으로 표시하지 않습니다. 도입·대사·상태를 각각 임의 확정하지 않습니다.

### 기존 저장과 요청 호환

- `conversation`이 없는 저장은 안정적인 ID의 공개 방으로 읽습니다. 조회로 DB를 수정하지 않고 다음 정상 쓰기 때 저장합니다.
- 기존 `recipient_id`는 정식 인물 ID 또는 `newcomer/secretary` 역할을 받습니다. 생략·null이면 저장된 방을 사용합니다. 값을 지정하면 이번 턴만 1:1로 처리하며 `turn.conversation`은 그 청중, `game.conversation`은 기존 저장 방을 가리킵니다. 1:1 선택지는 422이고, 1:1 자유 입력으로 활동·수치를 실행하지 않습니다.
- 선택 필드를 생략한 요청의 fingerprint는 기존 형식을 유지합니다. 늦게 재시도한 요청은 저장된 턴과 현재 게임 상태를 반환하며 과거 상대를 현재 방에 덮어쓰지 않습니다.
- 과거 턴에 방 스냅샷·종류가 없어도 읽으며 추가 상태는 기존 SQLite JSON에 저장합니다. `event_openings`가 없는 응답을 지원할 화면은 `event_openings ?? []`를 사용합니다.
- 저장에 도입이 없으면 현재 사건의 도입을 조회 응답에서 복원해 해당 사건의 첫 사용자 턴 앞에 배치합니다. 조회는 원본 DB를 수정하지 않고 다음 정상 쓰기 때 같은 ID로 저장합니다.
- 현재 화면에는 `conversation` 응답이 필요합니다. 연결 변경 시 백엔드를 먼저 배포하거나 함께 적용하고, 기존 요청·저장의 호환을 유지합니다.

## Part 1–2 프로토타입 연결

타이틀의 Part 2 시작 경로는 `{character_id: "a", scenario: "part2"}`로 생성한다. 기존 요청의 `scenario` 생략은 이전 축약 데모를 유지한다. Part 2는 이도·여울·사야를 자유 순서로 면담하고 한 명 선발 후 1~6개월차를 진행한다. 공개 대화는 기존 후보/신입·백하연을 유지한다. `p2_m01_training`에서만 리안·도하·세인 1:1 대상을 추가한다.

면담·선발로 후보가 바뀐 턴에서는 `turn.conversation`의 이전 인물이 결과 대사의 화자이고, `game.character`·`game.conversation`은 새 인물이다. 과거 대사를 현재 신입 이름으로 다시 표시하지 않는다. 도입 앵커·중복 요청·실패 재시도는 기존 계약과 같다. 완료 장면에서 결과를 확인하면 `ending.id="part2_complete"`로 시연을 종료한다. 24개월차 계약 결말과 구분한다.

웹 담당 대응: 타이틀의 기존 게임 시작·이야기 이어하기에서 도입과 면담, 월별 활동을 연결한다. 새 백엔드부터 적용하거나 웹과 함께 적용한다. 이전 백엔드는 `scenario` 필드를 거부한다. 상세 행동·판정·호환은 [Part 2 프로토타입](part2-prototype.md)을 따른다. 프런트의 생성 입력은 `CreateGameInput`을 사용한다.

## 현재 지원 범위와 미구현

- 상대 전환은 선택 신입과 백하연을 지원하며, 첫 달 `p2_m01_training`과 2개월차 `p2_m02_center`에서는 기존 멤버 3명과의 1:1 대화를 추가 지원합니다. 그 외 사건에서 기존 멤버와의 대화는 지원하지 않습니다. 독립 페르소나 콘솔의 7명 전환 가능 여부와 구분합니다.
- 게임 활동은 기본적으로 함께 대화에서 실행합니다. 2개월차는 모든 멤버와 대화한 뒤 전체 면담을 마무리하고, 버튼 또는 백하연과의 채팅으로 센터를 선택하면 성패 판정 없이 다음 달로 이동합니다. 다른 월별 화면의 1:1에서 활동 메뉴를 열면 먼저 함께 대화로 복귀합니다. 2개월차 전체 면담 마무리·센터 선택 전용 요청을 제외하면 1:1인 채로 행동을 전송할 때 서버가 거부합니다. 멤버와의 개인 면담은 게임 행동·스탯 변화로 처리하지 않습니다.
- 여러 멤버에게 훈련·휴식을 각각 배정하는 기능, 멤버별 독립 수치, 스트리밍 대사는 미구현입니다.
- 현재 도입 저장은 선형 시나리오에서 사건마다 한 번입니다. 같은 사건을 재방문하는 회차별 도입은 별도 설계가 필요합니다.
- 인물별 숨겨진 지식 원본·공개 허가는 서버 내부 상태입니다. 프런트로 전체 자료를 보내지 않습니다.

- 6개월: 백하연의 현재 스탯·반기 현황 브리핑 → 신입 예능 제안 → 면담·출연 결정 → 준비 이력에 따른 성공/실패 → 여섯 달 결산. 기획에 있는 예능 능력 상승 이력(0회 실패/1회 이상 성공)을 샘플 필드 `varietyGrowth`로 확인한다. 실제 캐릭터 능력치 API는 연결하지 않았다.
- 후속 웹/서버 연결: 서버에서 월별 면담 횟수·동적 스탯·단계·선택·4/5개월 판정·예능 준비 이력·쇼케이스 비용 정산 여부를 확정해 응답해야 한다. 그때 서버 응답 모델·`types.ts`·화면 어댑터를 함께 맞추고 데모 전용 상태 전이 함수를 서버 호출로 교체한다. 저장·재시도는 기존 서버 계약을 유지하며 클라이언트 계산을 서버 판정으로 사용하지 않는다. 기존 1개월의 3회 조건 등 실제 서버 프로토타입과의 규칙 통일도 후속 적용 사항이다.

### 개발용 진입점과 fixture 경계

Vite 개발 서버에서만 다음 경로를 사용한다(예시는 기본 포트). 프로덕션 빌드에는 개발 모듈이 포함되지 않는다.

| 경로 | 연결·저장 | 용도 |
|---|---|---|
| `/?playtest=center` | 실제 `/api`, demo provider만 허용. `prom-center-playtest-game`에 별도 ID | 면담·첫 달·멤버 면담을 API로 준비하고 센터 선택 직전 열기 |

| `/?monthlyFixture=1` | API 호출 없음. `prom-dev-monthly-fixture-v1`에 별도 브라우저 저장 | 3~24개월 공통 화면·조사 카드·네 결과·세 엔딩·오류 표시 확인 |

- Fixture 도구의 `저장 전 실패`는 아무 변화 없이 같은 요청 재시도를 제공하고, `저장 후 응답 유실`은 fixture 저장만 반영한 뒤 캐시된 결과를 한 번 복원한다. 실제 서버 장애 검증은 pytest의 모델 실패·롤백·중복 요청 테스트로 별도 수행한다.

### 2026-11-09 · 백하연 채팅으로 센터 선택·이유 보충

- 영입 후 팀 안내의 월별 활동 문구는 `대표님의 지시는 한 달 단위의 활동으로 진행됩니다.` 한 문장만 표시한다. 이어지는 첫 달 도입에서 실제 과제를 안내한다.

- 이유가 부족하면 기존 백하연의 보충 질문이 대사로 나오고 입력창은 빈 새 메시지 상태가 된다. 사용자가 이유를 다시 붙여넣거나 기존 입력을 수정할 필요가 없다. 서버의 `State.center_choice_draft`는 미확정 멤버와 실제 설명 턴 ID를 보존한다. 이어진 설명을 이전 선택·이유와 함께 평가하며, 기록에는 각 사용자 메시지를 원문 그대로 따로 저장한다.
- 단순 질문·가정·인사는 선택·평가로 확정하지 않는다. 명시적인 선택 취소는 미확정 선택을 해제한다. 다른 멤버로 선택을 바꾸면 이전 멤버의 이유를 자동 승계하지 않는다. 후보가 불명확하면 이름을 다시 묻고 수치·현재 달을 유지한다. `center_interviews.pending_member_id`로 서버의 미확정 후보를 조회할 수 있다.
- 대화 해석은 `interpret_center_choice`를 사용하고 평가는 기존 `evaluate_center`와 인용 검증을 사용한다. NPC 개인 면담 원문은 평가자에게만 전달하며, 백하연의 선택 대화 해석에는 명단·미확정 후보·사용자-백하연 대화만 전달한다. 성공/실패·효과·다음 달 전환은 서버가 확정한다. `ai_trace.analysis_calls`는 선택 대화 해석, `evaluation_calls`는 근거 평가 호출 수다.
- 대화·미확정 후보·이전 설명은 서버 저장과 조회로 복원한다. 과거 선택 창에서 보충을 기다리는 저장도 기존 이유를 읽어 새 채팅으로 이어간다. 예전 브라우저의 선택 창 초안은 삭제하지 않지만 자동 제출하지 않는다. 해석/평가 오류는 저장하지 않고 기존 같은 요청 재시도·409 재조회 흐름을 사용한다.
- 백엔드를 먼저 적용한 뒤 `CenterInterview.tsx`, `App.tsx`, `ServerMonthly.tsx`, `types.ts`를 함께 적용한다. 기본값으로 과거 저장을 읽으며 이전 요청 fingerprint를 유지한다. 아래의 선택 팝업·기존 이유를 편집하는 보충 방식은 이 항목으로 대체한다.

### 2026-11-09 · 면담 일괄 마무리와 센터·이유 선택 창

- 2개월차는 멤버별 종료 버튼 대신 전체 `면담 마무리`를 한 번 사용한다. `finish_center_interviews` 행동을 보내며, 기존 `close_center_interview`도 같은 전체 마무리 의미로 호환한다. 멤버당 8회 상한은 유지하되 8회 도달 자체로 전체 면담을 끝내지 않는다. 모든 멤버의 성공 저장 대화가 1회 이상이어야 마무리된다.
- 대화가 없는 멤버가 있으면 HTTP 200으로 백하연의 안내 턴을 저장하고 현재 대화방·스탯·미완료 상태를 유지한다. `center_interviews`에 `can_finish`, `missing_member_ids`, `finish_notice`, `selection_feedback`를 추가했다. `ready_for_decision`은 전체 마무리가 확정돼야 true다. 부분적인 옛 멤버 종료 표시는 더 이상 입력을 잠그지 않으며, 예전에 네 명 모두 종료한 저장은 완료로 복원한다.
- 전체 마무리 성공 시 백하연 방으로 이동하고 ‘누구를 센터로 선택하시겠습니까?’ 창을 연다. 선택한 멤버·이유 초안은 `prom-center-choice:{game_id}`에 보관한다. 면담 기록은 같은 창에서 다시 읽는다. 닫았다가 `센터 선택하기`로 재개할 수 있다. 기존 합의/일방 통보 선택지와 자유 대화만으로는 센터를 확정하지 않는다.
- 확인 요청 예: `{request_id, state_version, input_type:"action", action_id:"select_center", text:"", center_member_id:"dahyun", center_reason:"면담에서 들은 이야기를 바탕으로 한 선택 이유"}`. `center_member_id/center_reason`은 이 요청에서만 사용한다. 잘못된 멤버·빈 이유·면담 미완료는 422다. 프런트가 평가 근거나 점수를 전송하지 않는다.
- 서버가 실제 면담 기록과 이유를 평가한 뒤 유효한 근거를 확인한다. 명확한 결과면 3개월차로 진행하며 `Game.center_selection={member_id,member_name,reason,outcome,feedback,provider}`를 유지한다. 이유가 불명확하면 `turn.outcome=pending`, `selection_feedback`에 백하연 질문이 오고 현재 사건·스탯을 유지한다. 창을 닫지 않고 이유를 보충해 새 요청 ID로 제출한다. 평가 오류·잘못된 모델 인용은 502로 저장하지 않고 창 안의 같은 요청 재시도를 사용한다. 409 재조회·쿠키·기존 요청의 fingerprint는 유지한다.
- `Turn.ai_trace.evaluation_calls`와 평가 프롬프트 버전을 추가했다. 실제 평가 항목·근거 원문은 일반 화면에 노출하지 않는다. 최종 센터는 6개월차 결산·기록에서도 확인한다. 비용·효과 중복 적용은 서버 캐시·버전으로 방지한다.
- 적용: 백엔드 모델·provider·평가 검증·전체 면담 마무리부터 적용한 뒤 `types.ts`, `App.tsx`, `CenterInterview.tsx`, `ServerMonthly.tsx`와 스타일을 함께 적용한다. 새 필드의 기본값으로 기존 저장을 읽으며 이미 3개월차 이후인 플레이를 되돌리지 않는다. 아래 이전 기록의 멤버별 마무리·기존 센터 판정과 백하연 자유 입력 확정은 이 항목으로 대체한다.

### 2026-11-05 · #18 자원 표시와 대기 상태

### 2026-11-05 · 면담 탐색·목록 복귀 버튼 정리

- 기존 `finish_interview`의 직접 진행 호환은 유지한다. 새로운 웹 흐름에서는 `close_interview`와 완료 후 목록 복귀를 나눠 사용한다. 백엔드의 행동·완료자 필드 추가 후 프런트 `types.ts`와 `ServerInterviewRoom.tsx`를 함께 적용한다.

### 2026-11-05 · 후보 면담 8회 제한·단일 상대 적용

### 2026-11-05 · 첫 달 멤버 대화·합숙 규칙 연결 (5단계)

- `SixMonthSave.playthroughId`는 서버 원본 ID와 같은 값이며 내장 모드의 재시작·검토용 새 게임 도구는 숨긴다. 신입은 실제 선발 ID로 전환하며 `Part3Save.sourceId`에도 원래 ID를 유지한다. Part 3 기록에는 같은 플레이의 이전 후보·월별 대화를 함께 표시한다.
- 서버 통신 실패와 5xx는 원본 요청을 유지해 재시도하고 409는 재조회한다. 서버 오류로 로컬 구간을 생성하지 않는다. 로컬 저장은 revision 확인·쓰기 성공 후 반영하며, 실패·다른 화면의 진행·손상은 오류로 표시하고 저장을 덮어쓰지 않는다. 후보 면담 대화방/목록 위치도 새로고침 후 복원한다.
- 호환: 기존 서버 3~6개월에 이미 대화 기록이 있으면 해당 서버 월을 재시작하지 않고 기존 경로로 마친 뒤 `p2_complete`에서 Part 3로 이어간다. 이전 독립 데모의 전역 키는 보존하며 다른 플레이와 자동 혼합하지 않는다. 웹 담당은 `App`, `ContinuedPlay`, `playthroughState`, `MonthTwoTransition`, 두 월별 화면·상태 모듈 및 스타일을 함께 적용한다. 서버 배포 순서 변경·이관은 필요 없다.
- 확인 범위: 프로덕션 빌드·프런트 상태 테스트 102개·관련 백엔드 pytest 55개. PC·모바일 에뮬레이션의 실제 서버(키 없는 demo provider) 후보 면담·1~2개월과 로컬 3~12개월 전체 전환, 새로고침·이어하기·중복 요청·오류·재시도·성공·실패 샘플을 구분해 검증한다. 실제 유료 AI·휴대전화 실기기·3~12개월 서버 동기화는 미검증/미구현이다. 4·5개월 임시 결과 판정은 기존 미확정 상태를 유지한다.
