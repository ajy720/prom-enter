# 두 명이 함께 개발하는 방법

[문서 안내](../README.md)

작업은 에이전트에게 맡겨도 된다. 사람이 확인할 것은 **이번에 바꿀 범위**, **실제로 동작하는지**, **상대 작업에 영향을 주는지**다.
에이전트가 따를 세부 규칙은 [AGENTS.md](../../AGENTS.md), 설치·실행은 [실행 안내](../guides/setup.md)에 있다.

## 기본 흐름

```text
개발: 최신 origin/main → 작업 브랜치 → 수정·검증·필요한 시점마다 커밋
완료한 작업을 main에 반영할 때: push → main 대상 PR → 검사·충돌 확인 → Squash merge → 원격 main 반영 확인
```

- `main`: 둘의 작업이 합쳐진 공용 버전. 실행 가능한 상태를 유지한다.
- 작업 브랜치: 한 가지 기능이나 수정을 진행하는 공간. `feat/web-chat`, `feat/ai-memory`, `fix/game-save`, `docs/team-workflow`처럼 짓는다. 사람별로 영구 브랜치를 두거나 `develop` 브랜치를 추가하지 않는다.
- PR(Pull Request): 작업 브랜치의 변경을 `main`에 합치기 위해 GitHub에 올리는 변경 묶음.
- Squash merge: PR의 여러 커밋을 하나로 묶어 `main`에 반영하는 방법.

작은 기능 하나가 동작하면 합친다. 화면 개편과 AI 전면 교체를 한 PR에 담지 않는다.
커밋은 개발 중 의미 있는 변경이 쌓일 때마다 나누어 한다. 한 브랜치에서 여러 번 커밋해도 되며, 관계없는 수정은 섞지 않는다.
PR은 커밋마다 생성하는 것이 아니라 **작업 단위가 완료된 브랜치를 `main`에 병합하려 할 때** 만든다. 이때 브랜치의 여러 커밋을 하나의 PR에 담을 수 있다.
작업 완료나 커밋만으로 PR 생성·병합을 자동 진행하지 않는다. 사용자가 요청한 범위에 맞춰 진행하며, `main` 반영을 요청받았다면 PR 생성부터 병합과 원격 반영 확인까지 수행한다. `main`에 직접 push하여 PR을 생략하지 않는다.
필수 리뷰·별도 승인·Issue 생성 절차는 없다. 작성자가 확인하고 합칠 수 있고, 서로 연결되는 변경은 상대에게 확인을 요청하면 좋다.
저장소의 필수 검사·보호 규칙은 충족해야 한다. 인증·권한·검사 실패 등으로 진행할 수 없으면 가능한 단계까지 마치고 중단 사유와 현재 상태를 보고한다.

커밋 메시지와 PR 제목·본문은 기본적으로 한국어로 작성한다. `feat:`, `fix:`, `docs:` 같은 접두사와 코드 식별자·경로·명령어는 원문을 유지해도 된다. Squash merge할 때 최종 커밋 제목·본문도 한국어인지 확인한다.

## 역할 나누기

AI 담당은 `backend/app/ai/`, 웹 담당은 `frontend/`와 백엔드의 HTTP·저장 코드를 주로 맡는다.
AI 코드도 백엔드 안에 있으므로 `backend/` 전체를 웹 담당 전용으로 보지 않는다.
데이터 형식(`models.py`), AI와 게임·저장을 잇는 연결부(`service.py`), 게임 규칙·콘텐츠·공통 설정은 양쪽에 영향을 줄 수 있다.

예를 들어 AI가 돌려주는 필드 이름을 바꾸면, 사용하는 서버 코드와 화면도 확인한다.
이때 “`emotion`에 새 값 `angry` 추가, 웹에서 이미지 대응 필요” 정도로 변경과 상대 할 일을 짧게 알리면 된다. 별도 합의 문서를 만들 필요는 없다.
상대가 수정 중인 연결부를 호환되지 않게 바꾸기 전에는 방향을 맞춘다.

## 에이전트에게 맡기는 예시

AGENTS.md를 자동으로 읽지 않는 도구에도 아래처럼 요청한다.
브랜치 이름은 작업에 맞게 바꾼다.

```text
AGENTS.md를 읽고 따라줘.
이번 작업은 채팅 화면에서 답변을 기다리는 동안 로딩 표시를 넣는 거야.
현재 변경을 보존하고, 새 작업이면 최신 origin/main에서 feat/web-chat-loading 브랜치를 만들어줘.
이미 이 작업의 브랜치나 PR이 있으면 거기에서 이어가줘.
필요한 부분을 수정하고 검증한 뒤 작업 단위로 커밋·push하고 main 대상 PR을 만들어줘.
커밋 메시지와 PR 제목·본문은 한국어로 작성해줘.
PR에는 변경 이유, 확인한 동작과 검증 결과, 상대 파트가 알아야 할 점만 짧게 적고,
필수 검사와 충돌을 확인한 뒤 Squash merge하고 원격 main 반영까지 확인해줘.
```

위 예시는 `main` 병합까지 맡기는 요청이다. 개발 도중의 커밋마다 PR을 만들라는 뜻은 아니다.
PR까지만 필요하면 “PR까지만 만들고 병합하지 마”, 로컬 수정만 필요하면 “수정과 검증까지만 하고 커밋·push는 하지 마”라고 범위를 제한한다.

## Git을 직접 다룰 때

각자 자기 컴퓨터의 clone에서 작업한다. 아래 명령은 프로젝트 루트에서 실행한다.
처음 설치와 실행은 [실행 안내](../guides/setup.md)를 따른다.

새 작업 시작:

```sh
git status
git fetch origin
git switch -c feat/web-chat-loading origin/main
```

`git status`에 아직 커밋하지 않은 변경이 나오면, 먼저 그 작업을 마무리하거나 에이전트에게 보존한 채 정리하도록 요청한다. 그대로 위 명령을 모두 실행하거나 변경을 삭제하지 않는다.
같은 작업을 이어가는 중이면 기존 작업 브랜치를 사용한다.

수정·검증 후 올리기(아래 파일과 메시지는 예시):

```sh
git diff
git add frontend/src/App.tsx frontend/src/style.css
git diff --cached
git commit -m "feat: 채팅 응답 대기 표시 추가"
git push -u origin feat/web-chat-loading
```

`git add`에는 이번 작업 파일만 지정한다. 이후 GitHub에서 작업 브랜치 → `main`으로 PR을 만든다.
변경 내용과 실행 결과를 확인하고 **Squash and merge**로 합친다.
필수 검사가 있다면 통과 여부를 확인하고, 병합 후 PR이 병합 상태인지와 병합 커밋이 원격 `main`에 포함됐는지 확인한다.
병합된 브랜치에 다음 작업을 계속 쌓지 말고, 새 작업 시작 명령에서 새 이름을 사용한다.

작업 중 상대의 최신 변경이 필요하면, 내 작업을 먼저 커밋한 뒤 **작업 브랜치에서** 실행한다.

```sh
git fetch origin
git merge origin/main
```

충돌이 나면 에이전트에게 “양쪽 변경을 보존하면서 충돌을 해결하고 관련 동작을 확인해줘”라고 맡긴다.
의도가 불분명한 부분만 상대와 확인한다. 강제 push나 한쪽 변경 삭제로 해결하지 않는다.

## 합치기 전에 확인할 것

변경별 테스트·빌드 명령과 수동 점검은 [테스트와 AI 평가](../guides/testing.md)를 따른다.

화면을 바꿨으면 직접 해당 화면을 눌러보고, AI·웹 연결을 바꿨으면 데모로 입력 → 응답 → 상태 반영까지 확인한다.
문서만 바꿨으면 링크·경로·내용만 확인하면 된다. 실제 AI 품질을 확인하려는 작업은 별도로 모델을 연결해 검증한다.
문제가 확인되면 해결하고 합치며, 확인하지 못한 내용은 PR에 그대로 적는다.

PR 설명은 “응답 대기 중 중복 입력을 막기 위해 로딩 표시를 추가했습니다. 프런트 빌드와 데모 입력을 확인했습니다.” 정도면 충분하다. 상대 파트 영향이나 중요한 미확인 사항이 있을 때만 덧붙인다.
완료 보고에는 커밋 상태와 실제 검증 결과를 짧게 남긴다. PR 생성·병합을 진행한 경우 PR 링크와 `main` 반영 여부도 남긴다. 진행이 막혔다면 완료로 표현하지 않고 중단 사유와 남은 단계를 적는다.
